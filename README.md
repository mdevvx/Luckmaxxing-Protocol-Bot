# Luckmaxxing Protocol Bot

A Discord bot that delivers an 8-day gamified luck-cultivation training program through interactive dialogue-based conversations. Users enroll with a unique code, get a private training thread, and progress through daily lessons by clicking through a coach/student dialogue format — or, on days with a video assigned, by watching a tracked video on the website.

---

## Features

- Private training **thread** per user, created under a configured parent channel (support-ticket style)
- Interactive dialogue — Gamblor responses are clickable buttons
- **Video days:** any day can carry a hosted video instead of dialogue; the thread gets a tracked `/watch` link instead of the text exchange
- A "report to Papi" DM ritual right after enrollment, so the bot can reliably reach the user outside their thread
- Intro + Day 1 delivered immediately on enrollment; Days 2–8 sent automatically on a daily schedule
- **Two-role system:** enrollment role assigned on sign-up, swapped for a completion role when training finishes
- Single-use enrollment codes generated by admins
- Full activity logging to a configurable log channel
- Per-server toggle — bot can be enabled/disabled independently on every server
- Guards prevent `/setup` running before the server is configured
- Persistent views — buttons survive bot restarts
- Single reminder message if a user hasn't responded ~24 hours after content is delivered (no auto-removal)

## Setup

### 1. Clone and install dependencies

```bash
pip install -r requirements.txt
```

### 2. Create your `.env` file

```env
DISCORD_BOT_TOKEN=your_bot_token_here
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_KEY=your_service_role_key_here
LOG_LEVEL=INFO
WATCH_BASE_URL=https://hypergamble.bet/watch
```

> **Important:** Use the `service_role` key from Supabase → Settings → API, **not** the `anon` key.

`WATCH_BASE_URL` is optional — it defaults to the value above. It's the tracked video page video days link out to (see [Video Days](#video-days)).

### 3. Run the database schema

Open your Supabase project → SQL Editor → paste the contents of `supabase_schema.sql` → Run. Safe to re-run any time — every statement is idempotent (`IF NOT EXISTS` / `ON CONFLICT DO NOTHING`).

This creates 7 tables: `enrollments`, `guild_settings`, `daily_progress`, `enrollment_ids`, `video_watches`, `issued_watch_tokens`, `training_videos` — see [Database Tables](#database-tables) for what each one does.

### 4. Enable Discord intents

In the [Discord Developer Portal](https://discord.com/developers/applications):

- Bot → enable **Server Members Intent** and **Message Content Intent**

### 5. Sync slash commands

There's no standalone sync script — use the bot's own `$sync` text command after it's running:

```
$sync
```

Send this in any channel the bot can see, as the bot owner or a server admin. It registers commands to that server instantly and clears any stale global commands. Run it again whenever commands change (e.g. after adding `/setvideo`).

### 6. Start the bot

```bash
python bot.py
```

## Server Setup (Admin — do this in order)

Once the bot is in your server, run these commands in order:

### Step 1 — Configure the server

```
/configure role:@Baby Gamblor completion_role:@Luckmaxxed Gamblor threads_channel:#training log_channel:#bot-logs
```

All options are optional and can be set separately or together. Without a role, completion role, and threads channel, `/setup` will be blocked.

| Option            | Description                                                             |
| ----------------- | ----------------------------------------------------------------------- |
| `role`            | Role assigned to users when they enroll (e.g. Baby Gamblor)             |
| `completion_role` | Role assigned when a user finishes all 8 days (e.g. Luckmaxxed Gamblor) |
| `threads_channel` | Parent text channel private training threads are created under          |
| `log_channel`     | Channel where the bot posts all activity logs                           |

### Step 2 — Post the enrollment message

```
/setup
```

Creates the `#luckmaxxing-protocol` channel (if it doesn't exist) and posts the enrollment embed with the Enroll button.

### Step 3 — Generate enrollment codes

```
/generateid count:10
```

Creates single-use codes to share with members. Each code can only be used once.

## User Enrollment Flow

1. User clicks **Enroll in Luckmaxxing Protocol** in `#luckmaxxing-protocol`
2. A modal appears — user enters their 5-character enrollment code
3. Bot verifies the code and atomically marks it as used
4. Bot assigns the configured **enrollment role**
5. Bot creates a private **thread** (`luckmaxx-{username}`) under the configured threads channel
6. Bot posts a pinned onboarding embed, followed by the "report to Papi" DM ritual prompt
7. Intro dialogue starts immediately, followed by Day 1
8. Days 2–8 are delivered automatically on a daily schedule

If thread creation fails at step 5, the user is automatically unenrolled and the enrollment role is removed. The DM ritual (step 6) is non-blocking — training proceeds even if the user never clicks it or has DMs closed.

## Video Days

Any day (1–8) can be assigned a hosted video instead of dialogue. If a `training_videos` row exists for that day, the user gets a "Watch Video" link card instead of the text exchange; otherwise the day falls back to its normal dialogue.

Set or update a day's video with:

```
/setvideo day:1 url:https://<project-ref>.supabase.co/storage/v1/object/public/<bucket>/day1.mp4 caption:Optional text
```

- The URL must be `https://` and **must not** be a signed Supabase Storage URL (`/object/sign/...?token=...`) — those expire. Use a **public** bucket and its `/object/public/...` link, which never expires. The command rejects signed URLs automatically.
- Each watch link the bot sends is unique per user/day — it embeds a random token, the day number, and the user's Discord ID, and that token is recorded in `issued_watch_tokens` so it can later be validated against forged submissions (the `/watch` page itself has no login).

> **Known gap:** there is currently no background job in this codebase that reads `video_watches` and advances a user's day after they watch. `VideoDayView` is a link-only card — nothing here calls the day-completion logic for video days yet. Until that consumer job exists, assigning a video to a day a live user is on will leave them stuck with no way to progress. Safe to use for testing with `/progress`/`/unenroll` in the loop; not yet safe for a day real users are actively on.

## Training Completion Flow

When a user clicks through the final button on Day 8:

1. Bot posts the congratulations message in the training thread
2. Bot **removes the enrollment role** from the user
3. Bot **assigns the completion role** to the user
4. Completion is logged to the activity log channel
5. The enrollment row is marked `completed = True` — the user is excluded from all further task-loop checks

---

## Reminder System

There is no automatic removal for inactivity. Instead:

- The daily task loop checks every 30 minutes whether each user's ~24-hour content window has elapsed
- If they haven't clicked anything since their last day was delivered, they get **one reminder message** in their training thread ("Day X training is waiting for you") and the alert timer resets
- If they respond, the next day's content is delivered as normal
- Nothing is deleted, no role is removed, and the user is never unenrolled automatically — only an admin via `/unenroll` removes someone now

## Role Lifecycle

| Event                            | Enrollment Role | Completion Role |
| -------------------------------- | --------------- | --------------- |
| User enrolls                     | Assigned        | —               |
| Thread creation fails            | Removed         | —               |
| User completes Day 8             | Removed         | Assigned        |
| Admin `/unenroll` (mid-training) | Removed         | —               |
| Admin `/unenroll` (completed)    | —               | Removed         |

## Activity Logs

When a log channel is configured, the bot posts embeds for the following events:

| Event                | Trigger                             |
| -------------------- | ----------------------------------- |
| User Enrolled        | Successful enrollment               |
| Enrollment Failed    | Bad/used code, already enrolled     |
| Day Completed        | User finishes a day's dialogue      |
| Training Complete    | User finishes Day 8 (roles swapped) |
| User Unenrolled      | Admin uses `/unenroll`              |
| Bot Enabled/Disabled | Admin uses `/toggle`                |
| IDs Generated        | Admin uses `/generateid`            |
| Day Delivered        | Daily task loop sends a day         |

The single reminder message sent when a user hasn't responded is posted in their thread but is not currently mirrored to the log channel.

## Adding Training Content

Open `content/training.py`. Each day is a list of `(speaker, message)` tuples. Speaker is either `"Intern"` (coach) or `"Gamblors"` (student response).

```python
DAY_2 = [
    ("Intern", "Welcome to Day 2..."),
    ("Gamblors", "Ready, Chief!"),
    ("Intern", "Today we cover..."),
    ("Gamblors", "Understood!"),
    # Add as many exchanges as needed
]
```

- `"Intern"` lines display in the embed and the user reads them
- `"Gamblors"` lines become the clickable button the user presses to advance
- The last item in the list triggers the **Complete** button
- The day's `(speaker, message)` list must still be defined even if that day also has a video assigned via `/setvideo` — `_send_day` bails out early if `get_content(day)` is empty, video or not. The video, when present, replaces what gets *rendered* (a watch-link card instead of the dialogue); it doesn't remove the requirement to have dialogue content defined for that day.

## Bot Disabled Behaviour

When the bot is disabled via `/toggle off`:

- All commands return an ephemeral "bot is disabled" message
- The enrollment button in the protocol channel also shows a disabled message
- The daily task loop skips guilds where the bot is disabled
- `/toggle`, `$sync`, and `/configure` still work so admins can always recover

## Database Tables

| Table                  | Purpose                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `enrollments`          | One row per user per guild — tracks day, thread ID, completion status                  |
| `guild_settings`       | Per-guild config — bot toggle, threads channel, enrollment role, completion role, log channel |
| `enrollment_ids`       | Single-use enrollment codes with used/unused status                                    |
| `daily_progress`       | Analytics log of every day completion event                                            |
| `training_videos`      | One row per day (1–8) with its hosted video URL and optional caption — set via `/setvideo` |
| `video_watches`        | Written by the external `/watch` page (public, insert-only) when a user finishes a video |
| `issued_watch_tokens`  | Our own record of every watch-link token issued, for validating `video_watches` submissions against forgery |

## Logs

File logs are written to `logs/bot.log` with rotation (10 MB max, 5 backups). Console output is emoji-safe for Windows terminals.
